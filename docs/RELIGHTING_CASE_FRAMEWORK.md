# 重光照系统：作品集 STAR 框架

本稿依据 Supersplat-Viewer 的 `docs/重光照系统项目介绍-STAR.md` 全文整理，已按用户确认的职责与跨章节分工接入网页正文。下述行号均指该原文。原文描述不等于本轮已通过代码与运行复测。

## 主线与首层摘要

**从扫描场景的明暗调整，到可编辑、可交付的局部光照。**

当前 3DGS 查看器的颜色来自重建结果，原有渲染路径无法直接获得所需的灯光响应。我负责查看器侧的重光照着色与交互接入：先打通全局亮度与局部光源，再以体积纹理支撑局部亮灯，补齐辉光、手电筒与配置交付，形成编辑与观看共用的效果链路。Shader 所有权与仲裁统一在 Shader 章节说明。

个人范围按用户确认限定为Viewer侧的光照与交互工作，不将平台重建、训练或SaaS全链路计为个人完成。Shader所有权机制只跨章引用。

## S｜为什么需要做

**用户要将白天采集的三维场景用于夜游、建筑亮灯和互动创作，而当前查看器主要呈现采集时的色彩。**

- 当前项目的标准 3DGS 渲染输入不提供可直接用于常规表面光照的面法线；直接放置引擎灯光不能获得需要的 splat 着色效果。
- 大场景同时运行 LOD 与流式加载，局部光照计算不能随笔刷点数在逐 splat 热路径里持续增长。
- 参数需要保存并在交付观看态恢复，不能只在编辑界面有效。

来源：§1.1–1.2，19–34行。表述限定为本项目路径，不将“所有 3DGS 都不能光照”写成普遍结论。

## T｜我需要交付什么

**在已有 PlayCanvas 查看器中，建立可调节、可保存、编辑与观看一致的实时光照路径。**

验收维度（目标，不声称本轮已完成复测）：

| 目标 | 可检查的结果 |
|---|---|
| 可创作 | 昼夜、点光/聚光、笔刷亮灯、局部辉光、手电筒均可独立操作 |
| 可交付 | 灯与区域配置保存后可恢复；编辑态与观看态显示一致 |
| 可共存 | 与开场和风格特效切换后无残留、覆盖或每帧重编译 |
| 可兼容 | GLSL / WGSL 对应实现；WebGL2 / WebGPU 分别验证 |
| 控制热路径 | 已提交亮灯点集不在每个 splat 上逐点遍历；烘焙不进入持续帧循环 |

来源：§1.1，21–23行；§2，53–76行；§5，359–386行。手电筒开关是会话态，不写入持久化目标（§3阶段5，278行）。

## A｜四个因果递进的关键行动

这里采用原文的技术依赖顺序，尚未利用提交历史确认具体开发日期。每一块首层仅展示“问题—决策—所得能力”；实现和代价展开查看。

### 01｜重光照着色：独立控制昼夜与局部灯光

**首层：原生灯光不能直接改变当前 splat 着色，因此从 night-mode 示例拆解材质注入点，并扩展为全局调光与局部灯光。**

- **问题**：单纯压暗 splat 会出现天空与场景割裂；没有可用表面法线时，常规漫反射模型不能直接照搬。
- **选择**：覆盖 `gsplatModifyVS` 的颜色入口；同一 `nightFade` 驱动 splat、主光和天空球。局部灯使用视线方向作伪法线，叠加距离/锥形衰减，并与昼夜参数解耦。
- **验证证据**：原文给出着色公式、场景同步逻辑、颜色线性化及 NaN 防护；对应文件为 `night-mode.ts`、`light.ts`。建议补录连续调光、白天单独开灯的画面，不能仅用静态截图证明交互有效。
- **取舍**：这是视角相关的视觉近似，不是恢复采集场景的物理光照；点光和聚光各固定最多10个，不保证超过容量时的选灯稳定性。

来源：§1.3，36–49行；§3阶段1–2，84–167行。

### 02｜世界空间亮灯区域：从笔刷烘焙到局部辉光

- **问题**：仅用屏幕笔触无法持久定位建筑选区，逐splat遍历点集又有容量和热路径成本。
- **选择**：拾取世界位置与半径，保存区域点集；将已提交区域烘焙为64³亮度场。splat调亮与Bloom屏幕mask从同一体积取数据。
- **结果**：空间区域可保存、换视角复用，已提交点数不再进入逐splat循环；CPU烘焙与固定体素精度仍有代价。
- **边界**：Bloom光晕仍是屏幕后处理，不是把屏幕效果烘焙为物理世界光照。草稿和多区域变化也可能重建体积，稳定内容按签名缓存，不能只写pointerup重建。

来源：STAR阶段3；当前源码与完整入口见`RELIGHTING_PIPELINE_EVIDENCE.md`。

#### 同一行动的渲染应用：同源体积重投影与回归修复

- **问题**：局部调亮与辉光范围不同、相机移动时跟屏滑动、近景体素点阵，以及预览和提交后的明暗跳变。
- **选择**：相机更新后的framerender重投影同源亮度场；已提交用体积、绘制中用实时点投影；按屏幕体素大小调stride与投影半径并平滑mask；预览只作用未提交区，阈值用smoothstep与knee。
- **结果与取舍**：处理空间源、相机时序与预览交接差异，接受投影采样、缓存精度及屏幕空间方法的边界。
- **证据**：当前bloom.ts及477ebe35、3beae67c等历史差异；未重新运行收益评测。

### 03｜后处理管线适配：保持色彩与编辑观看输出一致

- **问题**：HDR初始化顺序导致Bloom静默关闭；Reveal状态尚未创建时局部光提前开启；遗留参数误挂CameraFrame使整场变色，mesh/splat输出颜色空间不一致。
- **选择**：HDR先于enable；由settings提前判断开场并门控；按有效功能需求启用管线；在线性空间tone mapping后编码，统一相关材质并在退出时恢复快照。
- **结果**：从“局部效果可显示”推进到“按需启用、正确交接、编辑/观看同链路”。Bloom强度保持单一配置写入点。
- **证据**：60d37a96、0959a9a4、1ec97211及当前源码；全局Shader所有权与Composer细节仍集中在Shader章节。

### 04｜交互手电筒：处理指针跟随、遮挡与拾取竞争

- **问题**：单一光斑会穿墙，异步splat与同步mesh命中竞争会造成跳动和旧视角热点残留。
- **选择**：Fill/Hotspot与场景深度；mesh命中优先、取消冲突异步结果、滞回与相机变化时清理旧深度。
- **结果与边界**：扩展夜游交互；无深度时保留照明但无法保证防穿墙，开关为会话态。

来源：STAR阶段5。已有手电筒Demo只作应用入口，不据标题宣称覆盖全部边界验证。

### 配置交付与跨章节分工（并入结果，不另设行动）

灯与区域数据通过 settings 和编辑协议传递，编辑与观看复用效果链路；GLSL / WGSL 对应维护。手电筒开关为会话态，不将其归入配置持久化结果。

重光照只说明“作为贡献者接入统一 Shader 管理，处理材质重建与效果切换”，并提供跨章节入口。贡献者协议、所有权、优先级仲裁、材质写入与变体版本等完整原理集中在 [Shader 框架](SHADER_CASE_FRAMEWORK.md)，避免两个 section 重复论述，也不将仲裁描述为所有效果任意叠加。

来源：§3阶段6，282–310行；§5.1、5.3，361–386行。网页实现见 `src/components/RelightingCaseStudy.vue`。

### 延伸内容｜阴影与放置资产（放入可展开附录）

原文还包含引擎 shadow map 与屏幕空间叠影两条管线，主场景高斯只接影、不投影；mesh 深度预写与放置高斯遮挡补偿另行处理。它体现资产融合能力，但不应打断“调光→局部编辑→互动→系统收敛”的主线。

## R｜结果如何闭环

### 页面首层结果对应任务目标

1. **创作闭环**：从统一调光，扩展到可编辑的局部光源、亮灯区域与交互手电筒。
2. **复杂度闭环**：已提交笔刷点从逐 splat 循环转为固定亮度场采样，区域数量不再直接进入逐 splat 循环。
3. **管线闭环**：处理同源掩码、启用条件、Reveal门控与颜色空间回归，编辑和观看复用输出链。
4. **交付闭环**：编辑与观看共用效果链路，配置可保存恢复；作为贡献者接入统一 Shader 管理；所有权与仲裁详见 Shader 章节。

这些是原文记录的实现结果，不等于本轮已验证最新构建。以功能录像、实现代码、恢复与切换录屏共同支撑，而非用能力名称代替验证。

### 可展示的实现量与不能冒充的性能量

| 可从材料说明的实现量 | 展示口径 |
|---|---|
| `64³` 体积、`64 × 4096` R8 图集 | 数据表示规格，不是速度收益 |
| 已提交亮度场每 splat 一次采样 | 指该子路径，不是整个重光照或整个帧只有一次采样 |
| 10点光 + 10聚光容量 | 当前原文实现约束，不是性能评测结论 |
| GLSL + WGSL 两份实现 | 工程覆盖，不自动推出两个后端画面完全等价 |

原文没有给出固定设备、场景、点数、前后版本的 FPS / GPU耗时 / CPU烘焙耗时 / 内存对照。当前不填写提升百分比，不把“亿级场景可用”写成已经跑满亿级 splat 的实时渲染成绩，也不把18类问题计数作为性能指标。

来源：§3阶段2–3，164–215行；§4，334–355行；§5，359–386行。

## 证据边界与后续补录

- **个人范围**：原文“从零、独立设计”与实际本人负责模块是否一致；Composer/阴影中哪些属于本人主导、协作或沿用。
- **适用范围**：当前代码与原文的固定容量、体素规格、后端和阴影状态是否一致，接入正式版前按选定代码版本核对。
- **性能缺口**：复杂度推导可说明算法设计，尚不能替代相同设备/场景下的耗时与画质对照。
- **持久化口径**：原文§7短版称“全部能力可持久化”，但手电筒开关明确为会话态；网页只写灯与区域配置可持久化。
- **区域上限口径**：原文“无点数上限”应改成“移除 shader 固定点数组限制”，CPU烘焙和固定体素仍有限制。
- **阴影边界**：主高斯与放置高斯角色不同，不能将“主高斯不投影”扩大为所有高斯不投影，或反向宣称完整双向物理光照。
