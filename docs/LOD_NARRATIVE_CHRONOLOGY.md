# 大场景 LOD：按问题演进组织的叙事框架

核对日期：2026-10-28。依据用户回忆，结合 Supersplat-Viewer 的 Git / reflog、实际代码、STAR、《本地大场景测试验证集》和早期评测文档核实。当前只梳理内容，不修改网站或排版草案。

本文取代此前按“四类职责 / 三项贡献”作为主叙事的组织方式。职责分类只用于最终总结和证据索引。

## 核心故事线

**先改善视野内加载体验 → 对标原始调度并建立评测 → 测出细化速度与帧率取舍 → 修复运行时无效工作和重建路径 → 扩展场景后定位尺度与叶块粒度问题 → 继续验证预算利用与视野外降档 → 收敛设备默认配置。**

这是一条连续的研发过程：每一轮都说明“上轮解决了什么，又暴露了什么”。不能把后期认识倒置成一开始就明确知道的优化目标。

## 0. 起点：场景能够加载，但用户关注的区域没有及时变清晰

### 网站叙述底稿

亿级 3DGS 场景需要分级、分块加载。原有体验中，相机移动后，视野内细节恢复慢，旧请求可能占着下载槽位，部分资源即使到达也没有及时上屏；首屏进度与实际画面就绪状态也不一致。

最初受交付时间限制，尚未建立完善的统一评测体系，先以改善“打开场景、移动视角、停下看清”的基本体验为目标，完成第一轮优化。后续再通过系统性评测，对标原始调度、验证这轮改动的收益和代价。

“交付时间紧迫”由用户确认，属于项目背景；不根据提交记录推测具体工期或承诺日期。原STAR中“先建评测”的概括不能代替实际发生的先交付、再完善评测的顺序。

### 依据

v4阶段提交：`c8841f9d`（6/5 foreground优先）、`29a3837e`（6/9渐进拉取）、`b85c6637`（6/9初始进度）、`64516f18`（6/10 refinement activity）、`2ae761f3`（6/10视野中心优先）、`63ce4e3e`（6/11旧文件占槽与未上屏）、`2a09cf62`（6/12队列与并发槽同步）。STAR §1.2描述相关结构性问题。

不要在这一段先宣称已定位WorkBuffer或已证明叶块是根因；那是后续测试得到的认识。

## 1. 第一轮：优先处理当前视野，并加快交互后的细化（v4阶段）

### 网站叙述底稿

先在下载编排上优先处理当前视野和中心区域，按需求逐级拉取细档。相机移动、缩放或加载解锁后，开启有限帧数的 burst，提高短期加载与同步活跃度，使前景更快得到细化。并调整文件到达后的上屏时机和初始进度门控，减少队列占槽、进度提前结束或卡住等问题。

第一轮形成了可交互的 refinement 路径，但不同场景的实际收益与代价还缺少统一比较。

### 可确认细节

6/18从v4创建v5时的代码快照 `ac938faa:src/loaders/gsplat/lod/octree/refinement-controller.ts` 已有：

- movement burst：18帧；zoom：36帧；unlock：48帧；syncCooldown：3帧。
- desktop/mobile分状态并发、前景请求跟踪与pin引用等机制。
- 首屏粗档主动拉取与前景就绪统计。

这是历史快照参数，不能不加版本说明地写成当前默认参数；也不能把18–48帧统一换算成固定毫秒。

## 2. 为继续迭代建立可重复的评测流程（v5及实验支线）

### 网站叙述底稿

第一轮为赶交付优先实现了体验改进，但尚缺少完善的统一评测。继续迭代前，需要先将自定义 refinement 与原始 Supersplat-Viewer（PlayCanvas 原生 LOD 调度）对照，确认清晰恢复、帧率和资源开销分别改善了什么、付出了什么代价；再比较不同参数与后续优化版本。

为此将评测流程固化为可复用的 skill：固定基线版本、资产、设备、渲染后端、相机路线和缓存条件，批量记录首屏、变清晰时间、帧率、实际渲染点数与内存，并对照原始调度、自定义初版和后续迭代。配合 benchmark HUD 观察实时状态，用逐帧 profiler 和 CPU Profile 下钻异常，并增加上屏是否推进、是否误触发重建等正确性检查。

这些工具在多轮测试中逐步完善，不是所有能力在第一次创建分支时就一次完成。

### 两层基线与对照纪律

1. **外部基线**：指定版本的原始 Supersplat-Viewer / PlayCanvas 原生 LOD 调度，用于判断自定义调度的整体收益与代价。
2. **内部基线**：自定义 refinement 的前一稳定版本，用于判断某一轮改动是否有效、是否回归。

比较资产组织时另设资产变量实验；比较调度时尽量保持资产与画质目标一致，同时记录实际点负载。不得将不同文件规格、预算或引擎版本的差异全部归因于调度。

本地自定义Viewer中的 `lodRuntime=native` 对照路径，只有确认没有其他Viewer改动影响且条件一致后，才可称为原始基线的等价代理；它不自动等同于一份未修改的官方Viewer构建。原始Viewer提交、引擎版本和资产身份仍需在每组可发表结果中明确，不以随时间更新的origin/main作为永久基线。

## 3. 第一批评测发现：快速变清晰与稳定帧率存在取舍

### 网站叙述底稿

在南广场、Finland和Poland等场景中，评测开始暴露不同表现：有的场景很快变清晰，但帧率仍低；Poland的细粒度版本恢复细节较快，却带来更多节点和运行时开销，粗粒度版本帧率较稳定，但等待细节的时间更长。

因此，增加预取和更频繁上屏并不能单独解决体验问题。需要进一步区分下载、换档、CPU更新和资产组织各自的成本。

### 规格核对

- 早期《大场景评测（Playcanvas 2.20版）》记录上述现象，并明确提及native `512k / 16m`。
- 《LOD调度性能与内存细粒度Benchmark方案》明确对照`96k / 10m`和`512k / 16m`。
- 用户回忆的早期`96k / 256k / 512k`三档，目前尚未找到完整的同轮三档原始结果；不补造表格或结论数字。
- 后期8/10的物理打包对照是`96k / 192k / 256k hard`，另有`96k normal`。不能将它与早期512k对照拼成一个单变量实验。
- 此阶段写“细化速度、帧率与文件/叶块组织的取舍”。最终画质/性能/速度平衡还涉及后期budget选择，不能把两次不同实验混为一谈。

## 4. 第二轮：先修复运行时的无效工作与全量重建触发

### 网站叙述底稿

Profiler将问题进一步指向两个独立的运行时开销：首屏已经完成后仍逐帧执行整树检查，以及将LOD同步过度绑定到全局dirty，导致本可增量处理的更新触发WorkBuffer重建。

因此拆分请求渲染、LOD重算与结构变化的语义，通过World更新入口推进增量placement更新，并对同帧同步去重；首屏完成后停止不再需要的全树轮询。随后重新检查上屏是否推进，避免只减少执行次数却丢掉更新。

这一轮减少了重复CPU工作和不必要的重建触发，为后续比较资产与场景差异提供了更可靠的运行时基线。

## 5. 第三轮：跨场景测试，把尺度问题与叶块粒度问题分开验证

### 网站叙述底稿

运行时基线调整后，将测试扩展到武汉、京东、BDA、城建小学、Poland和金安桥等场景。进一步发现两类问题：固定的米制距离选档难以适应不同尺度与密度；大尺度场景又可能因空间切分过细，产生大量叶块、区间和内存块，增加更新成本。

尺度方面先验证基于场景范围的lodScaleAlign，随后尝试以代表splat屏幕投影尺寸选档的renderScale；资产方面固定场景、路线和预算进行分块门槛扫描，分开比较逻辑叶块数量与物理SOG大小。通过武汉等反例，确认分块策略需要按场景选择，而不是一律越粗或越细越好。

### renderScale试验的结果与决定

《本地大场景测试验证集》“新增lodRenderScale→测试效果”记录：城建小学1762.3万点、budget固定6M，调整屏幕投影选档阈值。下表时间由原始毫秒换算为秒，保留三个点位，不把它们包装成多轮统计。

| renderScale | 平均显示点数 | 点位1 / 2 / 3耗时（秒） | 首屏（秒） | 记录帧率 | 原文视觉评价 |
| --- | ---: | --- | ---: | ---: | --- |
| 1 | 4.01M | 12.197 / 17.801 / 12.200 | 22.085 | 97 | 未单独标注 |
| 2 | 3.26M | 10.401 / 18.202 / 12.201 | 29.581 | 106 | 未单独标注 |
| 4 | 1.86M | 9.001 / 12.800 / 9.400 | 25.961 | 120 | 效果尚可 |
| 6 | 1.24M | 6.600 / 7.601 / 6.601 | 22.032 | 120 | 未单独标注 |
| 8 | 0.84M | 9.400 / 4.600 / 5.601 | 15.000 | 120 | 效果较糊 |

**结果**：rs=1、2仍偏向追细，点位等待与pending较高；rs=4在这组测试中降低了点负载，三个点位耗时均缩短，帧率记录升至120；继续放宽到rs=8，部分点位等待进一步缩短，但原记录已评价为“效果较糊”。首屏并非随阈值单调改善，例如rs=4的25.961秒仍慢于rs=1的22.085秒。

**决定**：验证了“限制不必要细化可以减少加载和显示负载”的方向，但收益伴随画质变化，不能当作等画质加速。没有足够依据将一个阈值推广到所有场景，最终保留renderScale可选，默认仍采用distance。原文“效果尚可/较糊”是当次记录者的评价，本轮未重新评图；“帧率”未注明P50或平均值，沿用记录名称。

STAR §4另有“rs≥16才明显clamp”的阶段概括，与本表rs=4已明显降低点数的记录不同；两者未对齐资产、构建和参数，不合并为统一阈值结论。

### 叶块数量实验的结果与决定

8/11 Poland leaf-ladder原始结果，budget=2.5M、WebGPU、四个静态点位：

| 资产版本 | 逻辑叶块数 | 实际点数P50 | update P50 / P90（ms） | frame P50 / P90（ms） | 报告blurToClear P50（秒） |
| --- | ---: | ---: | --- | --- | ---: |
| hard，extent=0 | 4096 | 2.192M | 6.2 / 8.2 | 16.7 / 17.2 | 11.900 |
| extent=10，min16k | 16384 | 2.190M | 21.5 / 29.9 | 25.7 / 41.7 | 10.333 |
| extent=10，min8k | 32752 | 2.064M | 49.8 / 63.9 | 66.7 / 99.9 | 6.503 |

**结果**：这组资产梯度中，实际点数接近，而叶块数增加时update与frame的P50/P90均上升，支持“节点/块管理成本也是瓶颈”。减少块数并未让所有点位恢复更快：4096与32752叶块的四点耗时分别为33.833/21.158/10.071/11.900秒、33.730/26.061/5.713/6.503秒，各点有不同取舍。

**决定**：控制过细切分造成的管理开销，同时检查细节恢复和单次上传成本；不推广“块越粗越好”。该实验改变空间切分策略，不能把收益归因于某一个minChunk参数、物理文件大小或调度代码改动，也未证明两资产逐像素画质相同。四点位分位是报告原值，不代表大样本或重复运行的统计显著性。

来源：Viewer的`benchmark-reports/2026-08-11/poland-leaf-ladder/results.json`及同目录协议说明。

## 6. 最后一轮：预算没有有效用于当前视野，进一步调整预算闭环与OOF

### 网站叙述底稿

后续HUD增加Budget、Center、Edge和Out分区统计后，发现部分场景并未将可用细节预算有效用于当前视野。问题包括目标与下载的差异、粗档回退范围、默认参数覆盖，以及看过后留在视野外的细档占用。

因此进一步让下载目标对齐引擎预算，保留边缘请求最低权重、修正预算配置，并为视野外节点设置粗档目标。显示切换先确认粗档可用，再分批处理残留细档；同时修正OOF对budgetScale反馈的影响，防止目标钳制引发新的振荡。

验证重点从“总点数有没有顶满”进一步转为“预算是否合理分配、中央是否追齐目标”。

### 依据与边界

- `bad91848` /8/4新增budget相关HUD指标；`ceef9a24`、`b012c9be` /8/5移除本地rawOptimal、调整ladder和中央上屏统计。
- `257aeb88` /8/10“视锥内部顶满budget即可”；`bde8e76f` /8/10新增OOF。
- OOF预算侧、显示侧、idle drip以及钳前总量反馈的最终实现见当前`out-of-frustum-downgrade.ts`。不能将最终所有细节都归入最初的OOF提交。
- 欠填不一定是bug：资产/视觉目标本身低于budget时无须硬填满。OOF降低活动used，不承诺allocator capacity或全部VRAM立即回落。
- `e4bb3315` /8/13仍继续修已下载未上屏，说明前几轮并非一次性闭环所有上屏问题。

## 7. 收敛默认档位：按设备平衡精度、帧率与恢复速度

### 网站叙述底稿

预算有效参与选档后，更高预算通常意味着需要加载与显示更多细节，但对不同场景的速度和帧率影响不同。通过城建小学、南广场等多档测试，最终将桌面2.5M、移动端1M设为首次启动的默认性能档，同时保留更高质量档和显式预算覆盖。

这一步是基于不同场景取舍形成的产品默认配置，不宣称它对所有资产都是数学上的最优预算。

## 8. 最后总结（只在历程结束后出现）

### 最终完成了哪些改动

1. **加载与上屏调度**：视野/中心优先、渐进下载、有限帧burst、到达后推进显示与首屏进度门控，改善首轮交付的交互路径。
2. **运行时开销**：停止首屏完成后的整树轮询，区分渲染请求、LOD重算和结构变化，通过增量World更新与同帧去重减少无效重建触发。
3. **资产与尺度适配**：将逻辑叶块数、物理文件大小与尺度分别验证，约束过细切分的管理成本；renderScale经过效果验证后保留为可选方案。
4. **预算分配与默认配置**：下载目标对齐预算，视锥外细档退到粗档，修正反馈与上屏顺序；收敛首次启动默认为桌面2.5M、移动端1M。
5. **验证能力**：建立对标原始Supersplat-Viewer / PlayCanvas原生LOD及内部版本回归的skill化评测，结合HUD、逐帧Profiler和CPU Profile定位问题。
